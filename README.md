# Secretary Bot — auto-reply + self-learning FAQ

## Що робить

- Відповідає в бізнес-чатах (Telegram Business "Автоматизація чатів") на вхідні повідомлення.
- Спершу питає локальну Ollama, чи відповідає повідомлення клієнта одному з питань у базі FAQ.
- **Ollama працює як класифікатор, а не генератор**: модель лише визначає НОМЕР відповідного питання зі списку — сам текст відповіді береться один в один з `data/faq-knowledge.json`, без жодної генерації. Це усуває ризик, що модель "загубить" URL, спотворить форматування чи поверне порожню відповідь на складний текст.
- Якщо жодне питання не підходить (`matchedId: null`) — падає назад на заглушку "адміна нема на місці", текст якої залежить від години доби (з cooldown в 1 годину на користувача).
- Логує **всю** переписку (і клієнта, і адміна) в `data/conversation-log.jsonl`.
- Раз на добу (за розкладом cron) прогонює лог через Ollama, щоб знайти повторювані типові питання і відповіді адміна на них.
- Нові кандидати не додаються в базу автоматично — вони йдуть у чергу `data/faq-pending.json`, і адмін підтверджує/відхиляє їх командами в Telegram.
- Захищений від паралельних AI-запитів: черга (`queueOllamaCall`) не дає кільком зверненням до Ollama виконуватись одночасно (CPU однаково обробляє їх послідовно), і захист від дублів (`inFlightUsers`) ігнорує повторні повідомлення від того самого користувача, поки попереднє ще обробляється.

## Встановлення

```bash
cd secretary-bot
npm install
cp .env.example .env
# заповни .env: BOT_TOKEN, ADMIN_TELEGRAM_IDS (через кому, якщо адмінів кілька)
```

Переконайся, що Ollama встановлена і запущена (`systemctl status ollama`), і модель з `config/ollama-config.json` (`chatModel`/`analysisModel`) завантажена (`ollama pull qwen2.5:7b`).

Запуск (напряму або через PM2):

```bash
node bot.js
# або
pm2 start bot.js --name secretary-bot
pm2 save
```

## Структура

```
bot.js                      — точка входу, вся обробка апдейтів
config/
  auto-reply-config.json    — тексти заглушок за годинами, cooldown, таймзона, enabled
  ollama-config.json        — URL Ollama, моделі, таймаути, промпти (класифікатор + аналіз)
data/
  conversation-log.jsonl    — сирий лог переписки (append-only)
  faq-knowledge.json        — підтверджені пари питання/відповідь (джерело правди для відповідей)
  faq-pending.json          — кандидати, що очікують підтвердження
lib/
  storage.js                — читання/запис JSON з захистом від гонки записів
  conversationLogger.js     — логування + базова редакція чутливих даних
  ollama.js                 — виклики до Ollama: classifyMessage (чат), analyzeDailyLog (аналіз)
  faq.js                    — керування FAQ/чергою кандидатів, buildClassifierPrompt
  autoReply.js              — вибір тексту заглушки за годиною
cron/
  dailyFaqAnalysis.js       — задача аналізу денного логу
```

## Команди адміна (пиши боту напряму, не в бізнес-чаті)

- `/pending` — показати всіх кандидатів у черзі
- `/approve_<id>` — підтвердити кандидата, додати в FAQ
- `/reject_<id>` — відхилити кандидата
- `/analyze_now` — запустити аналіз логу за останню добу вручну (не чекаючи cron)

## Налаштування

- **Розклад заглушок** — `config/auto-reply-config.json`, зміни підхоплюються без рестарту (`fs.watchFile`). Поле `enabled: false` вимикає fallback-заглушку повністю (AI-класифікація продовжує працювати).
- **Автовідповідач загалом** — вмикається/вимикається через `.env`: `AUTO_REPLY_ENABLED=true|false`. На відміну від `config/*.json`, зміни в `.env` **потребують рестарту**: `pm2 restart secretary-bot --update-env`.
- **Промпт класифікатора** — `config/ollama-config.json`, поле `baseSystemPrompt`. Модель має ЛИШЕ визначати номер питання зі списку (`{"matchedId": N}` або `{"matchedId": null}`) — не міняй цю логіку на "генеруй відповідь сам", це повертає стару проблему зі спотвореними/порожніми відповідями.
- **Промпт денного аналізу** — `config/ollama-config.json`, поле `analysisSystemPrompt`.
- **Дисклеймер до AI-відповідей** — `config/ollama-config.json`, поле `aiDisclaimer`, додається до будь-якої знайденої відповіді з FAQ.
- **Час щоденного аналізу** — змінна `DAILY_ANALYSIS_CRON` в `.env` (формат cron, за замовчуванням `50 23 * * *`).
- **Таймаути Ollama** — `chatTimeoutMs` (класифікація одного повідомлення) і `analysisTimeoutMs` (аналіз денного логу) в `config/ollama-config.json`. Холодний старт моделі (перше звернення після простою) може займати 10-20с — таймаути мають це враховувати.
- **Приватність** — `lib/conversationLogger.js` вирізає довгі числові послідовності (номери карток/договорів/телефонів) та email перед тим, як текст піде в модель для аналізу. Це базовий фільтр, не 100% гарантія — за потреби розширюй `redactSensitive()`.

## Як додати нове питання в FAQ

Найшвидше — вручну відредагувати `data/faq-knowledge.json` (масив `{question, answer}`, підхоплюється на льоту):

```json
{
  "question": "Формулювання типового питання",
  "answer": "Точний текст відповіді, який піде клієнту без змін — URL, форматування, все як написано тут."
}
```

Або дочекатись, поки `/analyze_now` чи щоденний cron самі запропонують кандидата за реальною перепискою — тоді підтверджуєш командою `/approve_<id>`.

## Важливі нюанси

- Дані повністю залишаються на твоєму сервері (Ollama локальна), в зовнішні сервіси нічого не йде.
- Кандидати в FAQ ніколи не публікуються автоматично — тільки через явне `/approve_<id>`.
- Якщо Ollama недоступна або відповідає довше за таймаут — бот тихо falls back на заглушку за годиною, без падіння.
- **Папка `data/` не потрапляє в git** — там зберігається реальна переписка з клієнтами (лог, FAQ-база). При першому розгортанні створи файли вручну: `conversation-log.jsonl` (порожній), `faq-knowledge.json` (`[]`), `faq-pending.json` (`[]`).
- Обробка бізнес-повідомлень обгорнута в try/catch (`handleBusinessMessage`) — необроблена помилка в одному повідомленні не "вбиває" обробку наступних.
- `handlerTimeout: 300_000` виставлений явно при створенні `Telegraf` — дефолтні 90с Telegraf може не вистачити на холодний старт моделі + генерацію.
